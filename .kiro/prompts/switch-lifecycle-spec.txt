Read the steering files in .kiro/steering (product.md, tech.md, structure.md) first. Then write a complete Kiro spec for the feature "switch-lifecycle" of this product into three files: .kiro/specs/switch-lifecycle/requirements.md, .kiro/specs/switch-lifecycle/design.md and .kiro/specs/switch-lifecycle/tasks.md. Only write those three files; do not create code.

requirements.md: an introduction, then numbered requirements, each with a user story and acceptance criteria in EARS notation (WHEN/IF/WHILE ... THE SYSTEM SHALL ...). Cover: vault setup (author name, email, cadence days, grace days, reminder lead days, witnesses required); writing rich-text letters to a recipient (name, email); in-browser encryption; the two custody modes below; one-tap check-in; reminders before the deadline; grace period with urgent reminders and a last-call reminder; witness confirmation (k of n witnesses), witness denial ("they still live") which cancels the release and restarts a grace window; optional release-on-silence after N days of no witness response; release with a one-time open link per letter; the server deleting the sealed copy after it is opened; pause and resume; every cancel path back to alive; a local time machine and local outbox for demos; accessibility (WCAG AA, keyboard, reduced motion, screen-reader announcements).

Key scheme to specify in design.md: each letter has a random AES-GCM 256 content key K generated in the browser. K is split into two 32-byte halves with XOR: K = A xor B. The vault half B and the ciphertext are uploaded; the server never holds A in "keepsake" custody. A (the keepsake half) is given to the recipient by the author ahead of time out of band (a keepsake link whose URL fragment carries A, or a printed keepsake code). At release, the recipient's one-time link fetches ciphertext + B and combines them with A in the browser. In "vault" custody (a convenience mode), the server also stores A and puts it in the release link fragment; the UI must say plainly that in vault custody the operator could read the letter. Document honest security limits (server operator in vault mode, compromised author device, email account compromise, witnesses colluding, metadata the server sees).

design.md: architecture (core pure state machine, Hono app with ports Clock, VaultStore, Mailer; local adapters MachineClock, MemoryStore with JSON file, OutboxMailer; real adapters SystemClock, KvStore on Workers KV, ResendMailer; Cloudflare Worker with Cron Trigger), the state machine with states alive, reminder, grace, confirm, released, paused and every transition and event (checkIn, tick, confirm, deny, pause, resume), effects as data, idempotent tick, data model, HTTP API routes, the crypto scheme above, UI pages (vigil dashboard with a candle that burns down over the cadence, letter writing desk, witness page, keepsake page, recipient open page, time machine and outbox drawer), error handling and the testing strategy (Vitest unit tests for every transition and cancel path, crypto round trip, tamper and wrong-half cases, API lifecycle test, Playwright end-to-end test that writes a letter, fast-forwards time, confirms as a witness and opens the released letter as the recipient). Include a Mermaid state diagram.

tasks.md: an implementation plan as a numbered checklist of small coding tasks ("- [ ] 1. ...", with sub-tasks), each referencing the requirement numbers it satisfies, ordered so the app is runnable end to end early. Keep wording professional. Use invented sample people and example.com emails only.
